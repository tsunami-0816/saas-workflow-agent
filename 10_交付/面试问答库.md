## Q1（选型）为什么自研 DAG 引擎，不用 Flowable / Activiti？

**30 秒版**：这个项目的流程是「MQTT / 手动触发 → 6 类节点 → 分钟级结束」，没有人工任务、会签、长事务补偿，而 Flowable 的价值恰好都在这些地方。引入它要背 30+ 张 BPMN 表、部署器和表达式引擎；自研只有 1 个调度循环 + 6 个执行器，16GB 单机更可控。实测 M1 的 30 节点 / 30 连线保存重载一致，M2 的 100 实例并发不串租户。

- **追问 1：自研怎么保证流程无环、分支正确？**
  `DslValidator` 在保存时校验 6 类节点合法、边引用的节点存在、无环、入出度约束；执行时每轮只调度「所有前驱已终态」的 PENDING 节点，condition 未命中的分支标记 `SKIPPED` 而不是删除，回放时能看到「为什么没走」。
- **追问 2：服务重启时卡在 RUNNING 的执行怎么办？**
  `ExecutionSweeper` 在 `ApplicationRunner` 里把 RUNNING / WAITING 统一收敛为 FAILED，`fail_reason=engine_restart`。续跑要求节点幂等且外部副作用可重放，HTTP / Agent 节点不具备这个前提，所以选择「明确失败让用户重跑」，不让状态机撒谎。
- **追问 3：规模上限在哪？**
  调度是串行循环，同层节点不并行。30 节点实测没问题，上百节点要改成按层批量并行；这是当前明确的天花板。
- **答不上来时的诚实说法**：自研没有 BPMN 的可视化调试、补偿事务、子流程、会签。真要做审批流，我会直接上 Flowable，不在自研引擎上堆。

## Q2（选型）实时进度为什么用 SSE，不用 WebSocket？

**30 秒版**：执行状态是单向推送（服务端 → 浏览器），SSE 用原生 HTTP、自带断线重连、能复用 JWT 鉴权链路，不需要协议升级和心跳维护。验收实测能收到 `event:connected` 和 `event:node`（含节点快照 JSON）。

- **追问 1：断线后状态丢了怎么办？**
  前端按 `executionId` 先拉一次 `node_execution` 快照补齐历史，再续订 SSE；不依赖事件流本身做唯一真相。
- **追问 2：多实例部署时 `SseEmitter` 怎么办？**
  当前是内存对象，单机可用；多实例需要 Redis pub/sub 或 MQ 广播。这一块我没做，是明确的下版本项。
- **追问 3：什么情况下会换 WebSocket？**
  需要双向控制时，比如人工暂停 / 介入 / 在线协作画布。现在没有这类需求，上 WS 只会多维护一套连接生命周期。
- **答不上来时的诚实说法**：SSE 是 HTTP/1.1 长连接，浏览器同域并发连接数有限；我的场景同时只看一个执行详情，没碰到这个限制，但没做过压力验证。

## Q3（选型）额度扣减为什么用 Redis Lua，不用数据库行锁或 Redisson？

**30 秒版**：LLM 调用是高频小额写，`UPDATE ... WHERE token_used + ? <= token_total` 会在热点租户上形成行锁排队。Redis 单线程 + Lua 天然串行，一次脚本完成「key 缺失用 DB 初始化 → 判断余额 → DECRBY → 返回剩余」。验收实测 tokenTotal=1,000,000、used=5,189、Redis 余 994,811，账能对上。

- **追问 1：Redis 和 MySQL 怎么对账？**
  Redis 是准实时口径，DB 的 `tenant_quota.token_used` 只做对账和展示。每次 LLM 调用另写 `llm_call_log`（provider / model / token / cost / tenantId），验收时 6 条台账逐条有值。
- **追问 2：并发下 `token_used` 会不会丢更新？**
  会。当前是「读-改-写」，并发下有丢失更新可能，Redis 计数为准。正确做法是 `UPDATE ... SET token_used = token_used + ?` 原子累加。
- **追问 3：为什么不上 Redisson？**
  我只需要单 key 的原子脚本，不需要分布式锁管理器。16GB 单机、单人维护，少一个组件就少一份启动与排障成本。
- **答不上来时的诚实说法**：当前是**调用后扣减**，超额的那一次已经花掉了。改进是调用前按预估 token 预扣、调用后按实际结算差额，失败/超时释放预扣。

## Q4（最难）CrewAI 导入卡死 90 秒，怎么定位的？（失败日志 #15 / #16）

**30 秒版**：现象是 python-agent 重启后 `import crewai` CPU=0、无输出、90s+ 不退出。第一轮我误判为 chromadb / lancedb 原生扩展（#15），试了 `memory=False`、改存储目录、`stdin=DEVNULL` 都没用。第二轮用 `faulthandler` 打栈，栈顶是 `crewai_core/settings.py:98 get_writable_config_path` → `tempfile.mkstemp(dir=~/.config/crewai)`：PowerShell 能建文件，Python `os.open` 卡死；同命令在非沙箱 shell 里瞬时成功。根因是受限 Windows 环境下 import 期的写探测被阻塞。

- **追问 1：修法是什么？**
  在 `app/__init__.py` 里、`import crewai` 之前把 `crewai_core.settings.DEFAULT_CONFIG_PATH` 重定向到项目内 `agent-python/crewai_data`，实测 import 成功。
- **追问 2：为什么最后又把它删了？**
  修好 import 后又踩 `BaseLLM.call` 签名漂移（`from_task` / `from_agent` / `response_model`，失败日志 #17），适配器按旧版只写了 4 个参数。CrewAI 在 Windows 受限环境的集成成本超过收益，10-31 按 R2 降级删除，改 LangGraph `planner→executor→reviewer`。
- **追问 3：删了怎么保证 Agent 能力还在？**
  三角色状态机保留，LLM 出口统一回调 Java `/internal/llm/chat`。验收时 Agent 节点真调 `qwen-plus`，输出含真实推理链，`llm_call_log` 落 6 条。
- **答不上来时的诚实说法**：我没有把 CrewAI 跑成生产可用版本，只在旧版设计里出现过，不能当作 CrewAI 经验讲；真实经验是 LangGraph。

## Q5（最难）条件节点报 `Could not find variable payload.temp`，怎么查的？（失败日志 #22 / #33）

**30 秒版**：前端配置面板提示用户写 `payload.temp`，后端 `buildInput` 注入的 key 却是 `_payload`，5A / 5B 并行开发时变量命名空间没对齐。第一轮只给起点节点加了 `payload` 别名，c1 条件节点过了，但下游 s2 代码节点仍报同错——说明注入范围错了，不是命名错了：`buildInput` 只合并直接前驱输出，不含祖先。第二轮对所有节点统一注入 `payload` + `_payload`，并补祖先上下文，实测 temp=60 / 95 两分支都 SUCCESS（exec 19/20）。

- **追问 1：为什么不直接改前端提示？**
  存量 DSL 和用户已发布版本会坏，后端做兼容成本更低；双别名是过渡补丁。
- **追问 2：怎么防止下次再漂移？**
  6.5 步导出 OpenAPI + 前端调用一致性脚本，但只覆盖 HTTP 路径，不覆盖引擎变量命名空间；补了跨级引用的冒烟用例（NL 生成的 DSL 会自然引用触发节点 `t1`）。
- **追问 3：跨级引用为什么之前没测出来？**
  10-28 冒烟用例里的代码节点只写字面量，没覆盖「下游引用祖先」；NL 生成的 DSL 才会这样写，属于用例设计漏场景。
- **答不上来时的诚实说法**：双 key 是兼容补丁，不是好设计。下版本应统一变量命名 + DSL 版本迁移，而不是长期维护两个别名。

## Q6（最难）点「执行」直接返回 10500，日志里才看到 Redis 连的是 6381（失败日志 #21 / #29）

**30 秒版**：用户点执行，前端只显示「服务器内部错误」。curl 复现 `POST /api/v1/executions` 返回 `code=10500`，全局异常处理器把 `RedisConnectionFailureException: Connection refused: localhost:6381` 吞成了未知错误。根因是 `application.yml` 默认端口 6381、db3，本机 Redis 实际在 6379。Java 启动不做 Redis 就绪检查，第一次访问幂等 `SETNX` 才炸。改成 6379 / db0 并加启动参数覆盖后，curl 实测 `code=0`、execId=1 RUNNING。

- **追问 1：为什么花了 5 轮才修好？**
  当时同时有三层错位：swa-mysql 3310 未起、RabbitMQ compose 映射 5673 但 java 默认 5672、PowerShell 下 `-D` 参数被路径解析混淆（#19）。只能逐个探活收敛：先 `Test-NetConnection` 端口，再对齐 yml，再统一用环境变量代替 `-D`。
- **追问 2：为什么启动时不报错？**
  Spring Boot 数据源 / Redis 是懒连接，不是必需前置；可以加 `ApplicationRunner` 里 ping Redis/MySQL，把失败前移。
- **追问 3：怎么防回归？**
  把 `.env.example` 当交付模板并修正 6381→6379（#29 就是这个模板过期）；`env_preflight --verify-config` 在启动前比对配置与实际端口。
- **答不上来时的诚实说法**：这是配置治理问题，不是架构问题；现在靠脚本前置校验，没做运行时熔断或自动重连降级。

## Q7（再做一次）架构级改进：契约先行 + 机器门禁

**30 秒版**：再做一次我会先定 OpenAPI 和跨服务字段表（tenantId、`X-Internal-Token`、失败语义），再写两侧代码；把契约校验、联调、环境校验做成 CI 门禁，而不是联调时人肉对齐。40 条失败里有 23 条（57.5%）属于环境 / 配置 / 依赖 / 契约类，本来都能机器前置拦截。

- **追问 1：跨服务字段具体定什么？**
  Java → Python 的 `/agent/run` 必带 tenantId；Python → Java 的 `/internal/llm/chat` 必带 `X-Tenant-Id` 与 `X-Internal-Token`；失败统一 `HTTP 200 + status=FAILED`，不能有时 4xx 有时 200。这三条我实际都踩过（#23 / #24）。
- **追问 2：前端变量命名怎么定？**
  引擎输入固定注入 `payload`（对外文档唯一口径），保留 `_payload` 一个过渡版本，DSL 加 version 字段做迁移，而不是永久双写。
- **追问 3：错误码怎么统一？**
  当前业务错误统一 `HTTP 200 + code`，未映射路径反而 10500，前端两套判断（Q-025 / W1）。下版本做统一错误码表 + 4xx 映射。
- **答不上来时的诚实说法**：现有门禁是脚本级，部分靠人工跑，没有全量进 CI；契约脚本只覆盖 HTTP 路径，不覆盖引擎内部变量。

## Q8（再做一次）额度改成预扣 + 结算；不引「只用一半」的依赖

**30 秒版**：额度从「调用后扣减」改成「调用前按预估 token 预扣 → 调用后按实际结算差额 → 失败释放」；DB `token_used` 改成 `UPDATE ... SET token_used = token_used + ?` 原子累加。选型上不再引 Spring Cloud BOM 和 CrewAI：前者只增依赖面没落地，后者在受限 Windows 环境 import 阻塞且签名漂移，最后被删。

- **追问 1：预估不准怎么办？**
  预扣设上限（如 max_tokens），实际结算多退少补；调用超时 / 异常必须释放预扣，否则额度会被永久占用。
- **追问 2：多 provider 成本怎么核？**
  单价配置表（每 1K token）+ 每次 `llm_call_log` 落 provider / model / prompt / completion / cost / latency，验收时 6 条台账可逐条对账。
- **追问 3：为什么说「引了就要用」？**
  JD 对账表 21 行复核后是真实落地 11 / 降级 7 / 纸面 3；纸面项（CrewAI、Qdrant、PostgreSQL）全是「文档里有、最终版没有」，面试一问就穿帮，不如一开始就不引。
- **答不上来时的诚实说法**：预扣结算是计划，不是现状；现状是调用后扣减 + 读改写，并发有丢失更新，Redis 为准、DB 只对账。

## Q9（细节）多租户隔离怎么落地？后台线程没有租户上下文怎么办？

**30 秒版**：tenantId 只从 JWT claim 取，写进 `TenantContext`（ThreadLocal）；MyBatis-Plus `TenantLineInnerInterceptor` 对所有表自动注入 / 过滤 `tenant_id`，`tenant` 系统表例外。前端禁传 tenantId，避免改 body 越权。

- **追问 1：MQ Worker / sweeper 没有请求上下文怎么办？**
  从 execution 反查 tenantId，显式 `TenantContext.set`，`finally` 清理，防止线程池复用串租户（这条是 #12 的真实修复）。
- **追问 2：漏设会怎样？**
  无上下文时给 0 而不是 null，`tenant_id=0` 匹配不到任何数据——失败方向是「查不到」，不是「查到别人」。
- **追问 3：怎么证明隔离有效？**
  M7 用例：dev_globex 读 / 写 / 删 tenant1 流程均被拒（业务码 20001 / 10403）；验收时 globex 列表为空，直连流程 1 返回 20001「流程不存在」，数据未泄露。
- **答不上来时的诚实说法**：这是应用层软隔离，靠拦截器覆盖所有 SQL；跨库、直连 SQL 会绕过。生产应加 DB 行级权限或独立 schema 兜底。

## Q10（细节）执行幂等怎么做？重复点「执行」会怎样？

**30 秒版**：`SETNX exec:idem:{userId}:{versionId}:{clientReqId}`，TTL 24h，值存 executionId；抢占成功才建实例并投 MQ，抢占失败直接返回既有 id。验收时同一 `clientReqId` 重发，返回的仍是 id=1，没有重复建实例。

- **追问 1：为什么幂等键要带 clientReqId？**
  只按 user + version 去重，会把「用户真的想再跑一次」也拦掉；请求 ID 必须由客户端生成。
- **追问 2：MQ 重复投递怎么办？**
  引擎看到 execution 已终态直接丢弃；延时节点恢复用 `WAITING→SUCCESS` 条件更新，重复恢复不会重复执行。
- **追问 3：抢锁成功后、写库前进程挂了？**
  会留下「键存在但查不到 execution」的 TTL 空窗，当前返回既有 ID 时查不到就报错。改进是「抢锁 → 写库 → 回填 ID」加补偿扫描。
- **答不上来时的诚实说法**：这不是分布式事务，一致性靠状态机条件更新；空窗存在，属于可接受但不优雅的取舍。

## Q11（细节）代码块 / 条件节点的表达式怎么防注入？（真实 P1，失败日志 #27）

**30 秒版**：用 Aviator 独立实例做沙箱，`FEATURE_SET = noneOf(赋值、循环、函数定义等)`，只保留表达式求值。8.5 安全扫描发现 CodeNodeExecutor 已沙箱，但 ConditionNodeExecutor 还在用全局 `AviatorEvaluator.execute`，DSL 条件表达式可调任意 Java 方法，这是 P1 代码注入；改成复用同一沙箱后回归 57 passed。

- **追问 1：怎么发现的？**
  secrets / SAST 脚本 + 逐条人工复核，不是靠测试用例撞出来的；测试只覆盖功能，不覆盖「用户能不能执行任意方法」。
- **追问 2：为什么不用 GraalVM JS？**
  体积和启动成本高，16GB 单机不划算；Aviator 只做表达式，能力边界小，攻击面也小。
- **追问 3：还剩什么风险？**
  超大正则、深递归仍可能吃 CPU；需要执行超时 + 独立线程池隔离，当前只有节点粒度超时兜底。
- **答不上来时的诚实说法**：这不是完整沙箱，是「特性裁剪」；真要做不可信代码执行，应换进程级隔离。

## Q12（细节）延时节点为什么用 RabbitMQ TTL + DLX，不用扫表？重启了怎么办？

**30 秒版**：延时节点投一条 TTL 消息到无消费者队列，过期经 DLX 转投 `execution.queue`，Worker 收到带 `resumeNodeId` 的消息，把节点 `WAITING→SUCCESS`，execution 从 WAITING 拉回 RUNNING 继续调度。验收实测 5s 延时节点先 WAITING，5s 后自动恢复，整体 36s 完成（其中 Agent 调用约 30s）。

- **追问 1：为什么不扫表？**
  扫表要处理扫描精度、PENDING 行的索引压力、多个 Worker 同时捞同一行的并发控制；DLX 把这些交给 Broker，秒级精度够用。
- **追问 2：TTL 队列有什么坑？**
  RabbitMQ 的 TTL 是队列级近似过期，存在队头阻塞，不适合跨数量级的长短延时混排；长延时应该用延时插件或时间轮。
- **追问 3：重启后 WAITING 实例怎么办？**
  sweeper 统一收敛为 FAILED（`engine_restart`），口径是「重启不假装续跑」，优先保证状态机不撒谎；这是我明确接受的取舍。
- **答不上来时的诚实说法**：牺牲了「重启后继续等」的用户体验，换取状态一致性；要支持续跑，得先让所有节点具备幂等与副作用重放能力。
